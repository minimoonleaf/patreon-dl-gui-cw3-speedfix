# patreon-dl-gui (カスタムビルド / v2.10.3-cw3)

**作成・メンテナンス: Moe Haduki (@hadukimoe)**  
**リリース日: 2026年9月21日**

本ドキュメントは、公式の `patreon-dl-gui` 2.10.0 をベースに、不具合修正および未知の URL プレフィックスへの対応機能を施したカスタムビルド版（Edition: cw3）の仕様と修正内容についてまとめたものです。

---

## 1. カスタムビルドの目的と背景

本カスタムビルドは、Patreon の Web サイト仕様変更に伴って発生した重大なダウンロード機能不全を解消することを目的としています。ツールの本来の機能を取り戻し、ユーザーが再び安定して利用できる環境へ復旧させるとともに、将来的な仕様変更にも耐えうる拡張性を提供するために作成されました。

### cw3 の立ち位置と作成動機

* **Issue #85 に対する私の最終的なカスタムビルド:** 本バージョン（cw3）は、Patreon の URL 変更問題（Issue #85）に対する私個人の最終回答（ファイナルビルド）となります。
* **実用上は cw2 で問題ありません:** 現在の Patreon でダウンロードが行えている場合は、無理に本バージョンへ移行する必要はありません。引き続き cw2 をご活用ください。
* **cw3 作成の動機（将来の未知のプレフィックスへの備え）:**
* Patreon 側の仕様変更により `/c/` に加えて突如 `/cw/` が現れたように、今後も `/cx/`, `/cy/`, `/cz/` といった新たなプレフィックスが登場する可能性があります。
* これまではプレフィックスが増えるたびにソースコードを修正し、バイナリを再ビルド・再配布する必要がありました。
* cw3 では設定ファイル（`custom-rules.json`）を 1 つ用意するだけで、**バイナリを再作成することなくユーザー側で新しいプレフィックスを即座にバイパスできる仕組み**を実装しました。

## 2. 2.10.0 からの累積修正内容

### ① cw1: 初期の機能復旧（Tian Sun さんによる貢献）

* **発生していた問題:** Patreon 側のフロントエンド内部データ構造が刷新されたことでページデータの解析が行えなくなり、「No target identified」エラーが発生していました。
* **修正内容:** Tian Sun さん（@tiansun2）による初期修正を導入し、ブラウザの現在 URL から直接ターゲットを抽出するフォールバック機構によって、基本的なダウンロード機能を復旧させました。

### ② cw2: 処理の洗練と個別投稿ページの復旧（PR #88 を参考）

* **cw1 で残っていた課題:** 基本的なダウンロードは復旧したものの、個別の投稿ページを直接開いた状態からダウンロードしようとするとエラーになる問題が残っていました。
* **修正内容:** @ma7m0d999 さんが PR #88 で提案されたスマートなアプローチを採用しました。正規表現に頼るのではなく、URL をスラッシュで分割し、先頭にプレフィックス（`c` や `cw`）があれば配列から `shift()` して切り落とす処理を実装しました。これにより既存の URL 判定ロジックがそのまま活用できるようになり、トップページ・個別投稿ページを問わず完全に動作が安定しました。

### ③ cw3: 外部設定による動的プレフィックス解決機能の実装

* **課題:** ソースコード内にプレフィックスをハードコードしている状態では、今後未知のプレフィックスが登場するたびにバイナリの再配布が必要になります。
* **修正内容:** `custom-rules.json` による動的プレフィックス除去ルールを導入しました。未知のプレフィックスが付与された URL であっても、外部設定に基づいてパスを正規化（`shift`）し、即座にダウンロードを継続できるよう拡張しました。

## 3. バージョン管理・UI表示の仕様設計

**修正の動機について:**

MSI インストーラーを配布するにあたり、公式バイナリとの混同を避けるため、Help メニューの About（アプリケーション情報）画面において「カスタムビルドであること」を明示する必要がありました。しかし、単純に `package.json` の `version` を書き換えると、Electron のインストーラー（WiX/MSI）やルートランチャーが誤動作を起こします。

### ① バージョン番号の 3 セグメント化（major.minor.patch）

`package.json` の `version` はインストール先フォルダ名（例: `app-2.10.3`）の決定に使用されますが、ここに 4 セグメント（例: `2.10.3.1`）や文字列を指定すると、ルートランチャー（`patreon-dl-gui.exe`）が `.installInfo.json` を正しくパースできず起動に失敗します。そのため、ベース仕様に従い純粋な 3 セグメント形式（`2.10.3`）を厳格に維持しています。

### ② UI表現とメタデータの分離

上記の制約を回避するため、`package.json` に独自のカスタムフィールドを追加定義しました。

* `"customName": "cw custom"`
* `"customEdition": "cw3"`

メインプロセス側（`SupportEvents.ts`）でこれらを読み込み、UI 側の About モーダル（`AboutModal.tsx`）内で文字列を動的に結合して表示しています。これにより、システム内部の整合性を保ちながら、画面上では一目でカスタム版（`patreon-dl-gui (cw custom)` / `v2.10.3-cw3`）であることが識別可能です。

### ③ 実際の記述例

上記の設計に基づき、今回のビルド（cw3）における `package.json` の該当部分は以下のように設定されています。

*⚠️ **注意:** 以下は該当箇所の抜粋です。ご自身でビルドされる際は、既存の `package.json` に対してこれらの項目を修正・追記するのみとし、ファイル全体をこの内容だけで上書きしないようご注意ください（ビルドスクリプトや依存関係が消失してしまいます）。*

```json
{
  "name": "patreon-dl-gui",
  "productName": "patreon-dl-gui",
  "version": "2.10.3",
  "customName": "cw custom",
  "customEdition": "cw3"
}
```

## 4. `custom-rules.json` の仕様と運用

### 設定ファイルの配置先と優先順位

1. **第 1 優先（推奨）:** `{Destination}/.patreon-dl/custom-rules.json`
   * 保存先フォルダーごとに異なるルールを適用したい場合に最適です。


2. **第 2 優先（グローバルフォールバック）:** `%APPDATA%/patreon-dl-gui/custom-rules.json`
   * 全クリエイター共通のグローバル設定として機能します。

※ デフォルトのプレフィックス（`c`, `cw`）は内部で対応済みです。設定ファイルの内容に重複があっても、内部で自動的に重複排除（ユニーク化）されるため安全です。

### 設定ファイルの記述方法

標準の `JSON.parse` を用いているため、`//` や `/* */` などの JavaScript 形式のコメントは使用できません。メモを残す場合はダミーキー（`_comment`）をご利用ください。

将来、Patreon 側で `cx`、`cy`、`cz` といった新しいプレフィックスが追加された場合の記述例は以下の通りです。

```json
{
  "_comment1": "新しいプレフィックスを追加した後は、ダウンロード前にブラウザの更新（↻）が必要です。",
  "_comment2": "配置先: [Destination]/.patreon-dl/custom-rules.json または %APPDATA%/patreon-dl-gui/custom-rules.json",
  "urlRules": {
    "stripPrefixes": [
      "cx",
      "cy",
      "cz"
    ]
  }
}

```

### 【重要】ルールの追加・編集時の操作手順

* アプリを起動したまま `custom-rules.json` を編集・修正することは可能です。
* **ただし、編集後はダウンロード実行ボタンを押す前に、必ずアプリ右側のブラウザ上部にある「更新（↻）」ボタンを押してページを再読み込みしてください。**
* 再読み込みによって最新のルールに基づいた URL の再解析が行われます。左側の Target 欄が正しく認識されたことを確認してからダウンロードを実行してください（アプリを再起動することでも反映されます）。

## 5. コラム / 技術的背景

### 「Start Download」ボタンで自動更新を行わない理由

* **シンプルな同期処理の維持:** 現在の「Start Download」ボタンは、すでに画面上で確定している Target 情報を拾い上げて確認画面を出すだけの安全な同期処理です。
* **非同期待ち合わせによる不具合防止:** ボタン押下時に「ページ再読み込み → DOM 解析完了待機 → 確認ダイアログ表示」という非同期フローを組むと、Cloudflare 認証や通信遅延時にアプリがフリーズするリスクが高まります。安全性を最優先し、解析はページロード時のみに限定しています。

### アプローチの変遷：コミュニティの知恵の統合

cw2 から cw3 へと進化する中で、URL 解析のアプローチには非常に興味深い技術的変遷がありました。

1. **初期の突破口（@tiansun2 さんの正規表現アプローチ）:**
Issue #85 が立ち上がった直後、@tiansun2 さんはいち早く「ブラウザの現在 URL を受け取り、正規表現を用いて直接ターゲットを抽出する」という対症療法的なフォールバック（`#analyzeCurrentURL`）を提示してくれました。これが多くのユーザーにとって最初の救いとなりました。
2. **処理の洗練（PR #88 のシフトアプローチ）:**
その後、PR #88（@ma7m0d999 さん）によって、「URL をスラッシュで分割し、先頭にプレフィックス（`c` や `cw`）があれば配列から `shift()` して切り落とす」という非常にスマートなアプローチが示されました。これにより、既存の URL 判定ロジックを全く壊すことなく柔軟なパス解析が可能となり、これが cw2 の強固な基盤となりました。
3. **cw3 での動的化（完成形）:**
そして今回の cw3 では、PR #88 で確立された「プレフィックスを `shift()` で切り落とす」という優れた設計をさらに拡張しました。切り落とす対象をソースコードに固定するのではなく、`custom-rules.json` から動的にリストを読み込んで切り落とす仕組みへと昇華させています。コミュニティの知恵が見事に融合し、将来の仕様変更にも耐えうる完成形となりました。

## 6. コード修正箇所の概要

* **`PatreonPageAnalyzer.ts`:**
  * `{Destination}/.patreon-dl/` および AppData からルールを動的に取得する `#getUrlPrefixes()` を追加。
  * 取得したプレフィックスを動的に除去して解析するよう `#analyzeURL()` を拡張。
  * `AnalyzerRequestOptions` に `destinationDir` を追加。

* **`MainWindow.ts`:**
  * エディタ生成時およびタブ切り替え時に、最新の `out.dir` をブラウザビューへ伝達。

* **`WebBrowserView.ts`:**
  * `#destinationDir` を保持し、解析呼び出し時にオプションとして渡すパイプラインを実装。
